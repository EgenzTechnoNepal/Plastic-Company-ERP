# API review checklist

**Scope:** Supplier, Customer, Item, Warehouse, Purchase Order, Gate Entry, GRN, QC, Inventory, Sales Order, Dispatch, Invoice, and CRM APIs.
**Review date:** 2026-10-07
**Method:** Static review of routed viewsets, serializers/services, shared tenant scope, DRF settings, and the exception handler. No API requests or tests were run for this review.

## Findings

1. **Tenant boundary is absent from compatibility `Record` APIs.** The compatibility model derives from `DomainRecord`, which has no company/organization field. Its viewset filters only by entity and active status; `HasModulePermission` enforces module RBAC but does not supply tenant filtering for these records. If tenant-specific data is stored in these routes, users with the module permission can list or retrieve records across companies. Prefer the typed endpoints above and do not treat compatibility routes as company-isolated.
2. **Inbound and QC writes do not validate every company-linked reference.** The shared related-field map does not include `purchase_order`, `shipment`, `gate_entry`, `receiving_bin`, `purchase_order_line`, or `grn`. The routed Import Shipment and Gate Entry serializers accept PO/shipment references; the GRN serializer accepts gate/shipment/bin references and nested lines; the QC serializer accepts a GRN reference. Their create/update paths rely on the generic mixin and these serializers do not add equivalent cross-company checks. As a result, a request can reference an object from another company even though the new/updated record itself is scoped. Validate each reference against the parent record's company in serializer or service logic.
3. **CRM update references are not fully company-checked.** `CompanyScopedMixin` checks related IDs from its `related_company_fields` mapping, which includes `supplier` but omits `customer` and `contact`. The typed `CrmActivityViewSet` and `PartyAddressViewSet` allow PATCH with those serializer fields and use the mixin's generic update path; a valid foreign-company customer/contact ID can therefore be accepted on update. Their custom create services do check ownership. Add explicit same-company validation to these update paths before relying on this invariant.
4. **Success response contracts are mixed.** Paginated lists use `{ "data": [...], "meta": {...} }`; some typed create/retrieve/update paths return the serializer object directly, while custom workflow actions often wrap it in `{ "data": ..., "meta": ... }`. Error responses are normalized separately to `{ "error": { "code", "message", "fields" } }`. Clients must currently handle more than one success shape.
5. **Validation errors are normalized by configuration, but clarity is not verified endpoint-by-endpoint.** DRF serializer and business-rule errors go through the ERP exception handler. No runtime request was made to confirm concrete messages or status codes for each invalid ID/payload.

## Shared controls and evidence

- DRF defaults to SimpleJWT authentication and `IsAuthenticated`; routed module viewsets additionally use `HasModulePermission`. RBAC endpoint tests exist in `Backend/apps/accounts/tests/test_rbac.py`.
- Typed company-owned viewsets use `CompanyScopedMixin`, which filters queryset/detail access and checks company/related-company access on writes. Its owner-company scope comes from active user roles and their branches.
- Existing API isolation tests cover typed inventory masters and CRM customers, among others; service tests cover selected PO/GRN, QC, dispatch, invoice, and CRM validation paths. These tests were inspected, not run as part of this review.
- Main references: `Backend/config/settings/base.py`, `Backend/apps/organization/company_scope.py`, `Backend/apps/accounts/permissions.py`, `Backend/apps/core/record_api.py`, `Backend/apps/core/documents.py`, `Backend/apps/core/pagination.py`, and `Backend/apps/core/exceptions.py`.

## Review outcome

Authentication and module-level authorization are configured consistently. The canonical typed endpoints generally enforce company-scoped list/detail access; this is supported by existing tests for selected modules, but was not runtime-verified across the full list. Do not claim tenant isolation for compatibility `Record` routes, and address the inbound/QC and CRM related-reference gaps before considering cross-company reference isolation complete. No source-code changes or fixes were made in this review.
